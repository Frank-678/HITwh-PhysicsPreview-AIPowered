# HITwh-PhysicsPreview-QuickFinish

> 基于运行时 DOM 解析、页面状态机与浏览器用户脚本的 SPA 自动化实验记录

## 项目简介

本项目围绕 HITwh 开放式实验系统中的预考核页面展开，核心目标不是简单地“写一个脚本”，而是系统性地解决一个典型的现代前端自动化问题：当目标系统是单页面应用（SPA）时，页面内容的切换不再依赖传统的 URL 跳转和整页刷新，而是由前端框架在同一个页面上下文中动态切换视图、请求数据并重绘 DOM。也正因如此，许多传统网页自动化中默认成立的前提，例如“进入新页面后地址栏会变化”“查看网页源代码即可拿到完整结构”“页面切换意味着旧节点已经不存在”，在这个系统里都不再可靠。

从开发日志的实际观察可以确认，该系统不是 iframe 架构，而是现代前端框架驱动的 SPA。点击“未通过 / 可考试”后，浏览器地址栏并不会变化，但页面内容已经切换为试题界面；进一步抓取 `#app` 运行时 DOM 后可以看到，列表页和答题页节点实际上可以同时存在于同一棵 DOM 树中，只是通过 `display: none` 控制显示与隐藏。这一发现直接决定了本项目的整体设计思路：自动化逻辑必须建立在“运行时真实 DOM”之上，而不能依赖初始页面源码或 URL 变化来推断状态。

## 研究背景

传统网页自动化通常依赖如下信号：

- 地址变化
- 整页刷新
- 静态源码结构稳定
- 页面间节点相互独立
- 跳转动作一定带来新的 DOM 上下文

但本项目对应系统打破了这些假设。开发日志记录表明，点击进入考试时，底层 JavaScript 会拦截默认跳转行为，通过异步请求获取数据，再由前端框架在页面内部更新视图。这意味着自动化脚本如果仍然沿用传统“抓源码—写选择器—等跳转”的模式，很容易失效。真正可行的方法是先分析页面机制，再围绕真实可见节点、按钮文本、卡片内容、表格内容和显隐关系建立状态机。

因此，这个仓库更准确的定位不是“某个固定页面的小脚本”，而是一个关于 **SPA 页面可见性判断、运行时 DOM 提取、用户脚本网络调用与状态机自动化设计** 的实践样例。

## 开发日志中的关键经验

### 1. 先判断页面是不是 SPA，再决定自动化策略

开发日志中最重要的经验之一，就是不要一上来就写脚本，而是先判断目标系统的页面组织方式。通过查看系统资源入口可以发现页面使用模块化脚本，进一步结合点击后 URL 不变、内容却变化的现象，可以确认这是一个标准的 SPA 场景。只有得出这个结论后，后续所有设计选择才是合理的。

这一步的价值在于，它直接排除了错误方向：

- 不需要去找 iframe
- 不能依赖跳转后的新页面事件
- 不能只看最初始的 HTML
- 不能把“节点存在”直接等同于“当前页面处于该状态”

### 2. 运行时 DOM 快照比“查看源码”更有价值

开发日志中明确记录了通过浏览器控制台执行：

```javascript
copy(document.querySelector("#app").innerHTML);
```

来抓取当前运行时页面内容。这个动作的重要性非常高，因为在 SPA 中，“查看网页源代码”拿到的往往只是最初挂载壳子，而题目、选项、按钮和真实视图结构都要等到前端运行后才会出现在内存中的 DOM 里。也就是说，自动化脚本真正应该对齐的对象不是服务器最初返回的 HTML，而是此刻浏览器已经渲染完成的真实节点树。

这个经验几乎决定了本项目的全部工程方法：遇到定位错误，不要先猜代码哪里写错，而应优先重新抓一份运行时 DOM，确认前端是否改了结构、类名或层级关系。

### 3. 节点存在不等于节点当前可用，必须引入“可见性”概念

从日志中抓到的 DOM 可以看到，列表页、题目区域和结果区域在某些时刻会同时挂载在 DOM 中，只是通过 `display: none` 切换显隐。这个现象说明，任何仅依赖 `querySelector` 是否返回节点的脚本都可能误判状态，因为隐藏区域的按钮、表格和卡片依然可能存在于文档中。

正因为如此，当前 `main.js` 中引入了 `isVisible(elem)` 作为辅助函数，通过 `offsetWidth`、`offsetHeight` 和 `offsetParent` 判断节点是不是“真实可见”。这个设计并不是细枝末节，而是 SPA 自动化里极其关键的一步：只看存在性会误判，只看文本也会误判，只有把“存在 + 文本 + 可见性”结合起来，状态识别才足够可靠。

### 4. 用按钮和语义文本判断状态，比单纯依赖结构更稳

当前脚本没有直接把页面状态写死成“第几个 div 可见就是哪一页”，而是通过语义更强的信号判断当前页面：

- 可见的“提交答案”按钮，表示当前处于答题页
- 可见的“返 回”按钮且不存在提交按钮，表示当前处于结果页
- 表格行中出现“未通过 + 可考试”，表示当前处于实验项目列表页

这种策略背后也来自开发日志的实践经验：在现代前端框架里，类名、层级、样式包装都可能调整，但语义按钮和业务文本往往更稳定。相比“写一串很长的 CSS 选择器”，利用界面中真实面向用户的语义信号，通常更抗前端改版。

### 5. API 调试要先确认模型，再确认返回结构，再调业务逻辑

开发日志完整记录了一个很典型的问题链：脚本最初已经能正确识别页面、提取题干和选项，但调用外部模型 API 时仍然出现“返回数据解析异常”。在这种情况下，真正有效的排查顺序不是立刻改 prompt，而是：

1. 先打印 HTTP 状态码
2. 再打印未经修饰的原始响应体
3. 检查响应 JSON 中是否真的有 `candidates`
4. 再验证使用的模型名称是不是当前 key 可用的模型

日志中还专门提到，通过请求模型列表接口可以看到哪些模型支持 `generateContent`，这一步帮助定位了“模型名不匹配”这类非代码语法错误。这个经验说明，浏览器脚本接入外部 API 时，问题并不总出在逻辑层；很多时候，能力边界、模型兼容性、密钥权限和响应结构变化才是首要排查目标。

### 6. 逐题请求虽然朴素，但在浏览器脚本环境里可能比批处理更稳定

开发日志中最有价值的网络经验之一，是对“单题请求”和“批处理请求”在浏览器脚本环境中的差异分析。表面上看，批处理似乎能减少调用次数，但实测却出现了网络底层通信中断、408 Request Timeout 等问题。日志进一步分析认为，当一次性打包多个题目后，请求体和模型计算量明显上升，服务端首字节返回时间变长，而浏览器所在环境的代理软件、校园网 NAT 或本地网关会在“长时间无数据回传”的空窗期里把连接误判为死连接并强制截断。

这条经验非常关键，因为它揭示了一个常被忽视的事实：用户脚本运行在浏览器里，不是运行在一台完全可控的后端服务器上。也就是说，设计请求策略时不仅要考虑应用层效率，还要考虑代理、Keep-Alive、闲置连接、RST 包、NAT 超时等环境因素。从开发日志的结论看，在当前场景下，短请求、快返回、快闭合的逐题调用反而是更现实的稳定方案。

### 7. 429 不是“代码挂了”，而是节流机制在工作

开发日志还记录了 429 限流场景以及提示中的退避时间信息。这里的经验同样很有代表性：调用失败并不总意味着代码逻辑错误，也可能只是服务端的正常频率控制。因此，遇到 429 时，正确做法不是不断重试轰炸，而是读取退避信息、增加等待时间，再继续尝试。

这也是为什么日志中提到通过调整 sleep 时间来配合实际调用节奏。脚本里的 `DELAY_MS` 不仅控制页面轮询速度，也会间接影响请求分布密度。对于这类浏览器自动化项目，节流往往是稳定性的一部分，而不是性能的敌人。

### 8. 提交后刷新页面不是多余动作，而是前后端状态同步手段

从开发日志可以看出，提交后即使后端状态已经变化，前端本地显示的“未通过 / 可考试”等标签也未必立即同步刷新。因此，当前脚本在结果页点击返回后又显式调用 `location.reload()`，其目的不是“保险起见乱刷新一下”，而是主动要求前端重新从后端拉取最新状态，防止本地缓存状态滞后。

这个经验对于很多前端系统都适用：异步操作成功并不自动意味着 UI 已经反映最新后端事实。尤其在没有完整状态管理可见性的外部脚本环境下，显式刷新往往是最稳的同步策略。

## 当前脚本实现概览

当前仓库中的 `main.js` 是一个标准 Tampermonkey 用户脚本，题头元数据已经较规范，包含：

- 名称
- 命名空间
- 版本号
- 描述
- 目标站点匹配规则
- `GM_xmlhttpRequest` 权限
- 外部 API 域连接声明
- `@run-at document-idle`

这说明脚本运行时机已经考虑到 SPA 初次渲染完成后的稳定阶段，而不是在文档尚未就绪时抢跑。

脚本主体大体可以概括为以下几个部分：

### 配置项

```javascript
const CONFIG = {
    API_KEY: "",
    MODEL: "gemini-2.5-flash",
    DELAY_MS: 3000
};
```

这些配置决定了网络调用目标与轮询节奏。特别是 `DELAY_MS`，它不只是一个“随便写的等待时间”，而是页面状态机稳定运行的重要参数。开发日志中已经反复体现等待时间对整体行为的影响，包括页面切换后的渲染等待、429 退避处理以及结果页返回后的刷新时机。

### 可见性判断函数

```javascript
function isVisible(elem) {
    return !!(elem && elem.offsetWidth > 0 && elem.offsetHeight > 0 && elem.offsetParent !== null);
}
```

这个函数在当前脚本中承担的是“过滤 SPA 中隐藏节点”的角色，是日志经验的直接落地实现。

### 大模型调用函数

当前脚本通过 `GM_xmlhttpRequest` 向外部 API 发送请求，构造 prompt，要求只返回 `A/B/C/D` 单个字母，并在响应处理中检查：

- HTTP 状态码
- 原始 JSON 解析是否成功
- `candidates` 是否存在
- 返回文本中能否匹配到合法选项字母

这套处理链条本身就反映了开发日志中的调试思路：先做结构防御，再做业务解释，避免因为直接深层访问 JSON 导致脚本崩掉。

### 主状态机

`runAgent()` 使用一个持续轮询的循环，根据按钮文本和表格内容判断页面状态，并分别执行：

- 列表页：查找包含“未通过”和“可考试”的行，然后点击进入
- 答题页：遍历题目卡片，提取题干与选项
- 结果页：点击返回，等待后调用 `location.reload()`

这套实现虽然朴素，但有两个明显优点：

1. 非常适合调试，日志易读
2. 在外部无法接入站点内部事件系统的前提下，轮询是简单且直接的控制方式

## DOM 解析策略

当前脚本不是“看到卡片就读”，而是先对 `.ant-card-bordered` 逐个检查，只处理包含 `"试题:"` 文本的卡片，再进一步提取具体内容。题干通过固定层级节点读取，选项通过 `.exam-radio` 逐项遍历，并把每个选项对应的 `input[type='radio']` 保存下来，形成“文字选项—真实点击节点”的映射。

这个策略的优点在于：

- 先过滤业务语义，再做细节定位
- 避免误把非题目卡片当题目处理
- 点击时直接操作原生 radio input，减少包装层对交互的干扰

当然，它也保留了一个现实局限：如果前端未来修改了内层结构，例如改变了题干容器层级、移除了某些内联样式或重命名了局部类名，这部分选择器可能需要重新对齐。因此，运行时 DOM 快照抓取仍然是后续维护时的首要手段。

## 已知问题与经验化结论

### 模型返回结构不稳定时，日志必须比逻辑更先完善

在这类项目中，最常见的误区之一是“接口一失败就改 prompt”。但从开发日志可以看到，真正有效的办法是先把探针插够，确保你知道失败发生在哪一层：

- 是请求没有发出去
- 是状态码不对
- 是返回不是预期 JSON
- 是 JSON 结构变了
- 还是模型没有按指定格式输出

如果没有这层日志，任何“优化”都只是在盲改。

### 批处理不一定能节约总成本

虽然理论上批处理能减少请求次数，但在浏览器脚本环境里，它可能带来更高的失败成本。一旦一个大请求在长等待后被环境截断，失去的不只是一次调用结果，还包括更长的重试链和更难追踪的环境噪声。从开发日志总结出的经验看，逐题模式虽然简单，却具有更好的可观测性和恢复性。

### 浏览器自动化项目要把“环境噪声”视为系统一部分

这个项目非常典型地展示了一个事实：脚本并不是运行在真空里。代理软件、校园网出口、浏览器扩展权限、空闲连接超时、前端框架重绘节奏，这些都不是外围因素，而是系统本身的一部分。只有接受这一点，自动化设计才会变得现实：不是追求理论上最优，而是追求在当前环境里最稳。

## 空题与失败处理

两个主脚本都会跟踪手动和自动点击的实验，只读取可见试题；无法确认名称时，不沿用旧实验名称。

- `LOAD_TIMEOUT_MS` 默认为 20000 毫秒。等待题目或进入答题页超时后，暂时跳过该实验并刷新；超时不代表已经确认老师未上传题目。
- 跳过列表只保存实验 ID，使用当前标签页的 `sessionStorage`，自动刷新后保留。
- 老师补充题目或网络恢复后，在 Tampermonkey 脚本菜单选择“重新尝试已跳过实验”，清除记录并重新开始。
- `MAX_RETRIES` 默认为 4，即每份试卷（DeepSeek）或每道题（Gemini）最多尝试 4 次；DeepSeek 的 429 同样计入次数。尝试耗尽后暂时跳过该实验并返回目录，继续其他实验，不提交空卷。DeepSeek 余额不足时暂停，充值后刷新可重新运行。
- 提交前检查是否每题都已选择答案。提交后等待页面切换；超时仍停留在答题页则记录该实验并返回目录，避免反复调用 API 和重复提交。
- 请只启用与所用模型对应的一个主脚本。

## 可选课程统计

在“预约选课”的实验列表页，将 `Additional-Features/统计可选择课程.js` 粘贴到浏览器控制台执行，点击“扫描未来 100 天”。扫描会逐项查看日期、大节、实验室和空闲/总座位，保留零空位结果，支持停止和 CSV 导出；不会预约座位。

`DAYS_AHEAD` 控制日期范围，`TIMEOUT_MS` 控制页面和请求等待上限。脚本只在扫描期间跟踪请求，结束或停止后恢复原方法；缓存结果无需等待固定的长延时。查询失败的时段会跳过并记录到控制台，不会用上一时段的座位冒充新结果。停止后保留已有结果，CSV 包含实验、日期、星期、周次、大节、开始时间、空闲座位、总座位、实验室九列。

## 安装方式

1. 安装支持用户脚本的浏览器扩展，例如 Tampermonkey
2. 新建脚本
3. 根据模型选择 `main-deepseek.js` 或 `main-gemini.js`，将内容粘贴进去
4. 保存
5. 根据需要自行填写配置项中的密钥与模型名称
6. 打开目标页面并通过浏览器控制台观察脚本输出

## 调试建议

如果后续继续维护这个项目，最建议遵循以下顺序：

### 第一步：先抓运行时 DOM

每次页面行为与预期不一致，先在控制台抓一份新的 `#app` 运行时内容，确认是不是前端结构变了。

### 第二步：再看状态识别

确认当前是卡在：

- 列表页识别
- 答题页识别
- 结果页识别
- 还是按钮点击后渲染未完成

### 第三步：最后再看接口层

确认模型名、响应格式、状态码和网络环境是否异常。

这个顺序与开发日志中的经验完全一致：不要一上来就怀疑所有层，而要先从最接近现象的一层开始定位。
